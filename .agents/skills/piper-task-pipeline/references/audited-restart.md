# 已结束的初始化暂态故障接续

这不是自动重试。原 `pair_scope`、故障、运行、回执及预算保留原值；新执行范围只有在用户明确同意故障后的新一轮有限预算后才创建。普通新 run-id、旧 owner、legacy 单步接口不能选用它；本次动作失败不改写为成功。

适用范围仅为：原运行已到期，只有完整厂家限位查询和最后一次 RGB 初始化；初始化四帧均有返回记录，唯一设备错误为 `joint_tracking_envelope`，无额外/未知帧、未决发送、保持或抓持历史；原宿主已有正常 close 回执，未遗留活动控制进程。close 只证明资源清理，不是机械停止。其他故障不得套用此入口。

`robot_tools.pair_restart.prepare_restart` 只读实际 SQLite 与原 close 日志，冻结全量历史摘要、原合同、当前修复源码、四帧及拟议预算，返回 proposal，不启动设备。默认新增执行窗口最多 900 秒；新步数与旧已用步数相加不得超出原步数上限。用户在故障后明确指定新的次数和时限时，使用 `budget_mode="explicit_user_budget_request"`，允许本次新窗口最多 500 次、3600 秒；旧已用次数另行累计，原记录不清零。仅已激活且预算完全匹配的 execution epoch 可让新宿主采用该范围，普通新 run 不因此扩大。用户的旧 restart、未修改目标的自动续轮和沉默不作为这次新增预算授权。

外层操作者保存真实原话、消息引用及收到时间，才调用不对普通 robot tool 暴露的 `activate_restart`。针对既有 proposal 的确认使用 `authorize_audited_new_attempt`；故障后用户新的明确预算指令使用 `authorize_explicit_budget_request`，可先于随后生成的 proposal，但必须绑定准确新预算与 proposal 哈希。用户主动修订目标、明确给出本轮新预算也按后一分支记录，不因为消息载体是目标恢复而遗漏新增指令；不将没有新授权内容的自动续轮冒充用户确认。已有这种明确授权就直接接续，不再要求对同样预算二次回复。

该管理事务占用现有执行锁、重核当前历史与代码，追加一次新执行范围及父子审计记录；不清旧故障、不改原起点或期限、不复制缓存，不自动发任何硬件帧。授权重放、旧 owner 或任意新 ID 均不能创建第二份预算。准备 proposal 与离线测试不等于已经完成激活。

激活后的唯一新宿主仍用原固定工具：新反馈取得当前健康、静止及模式；新 RGB 取得双臂空载/无接触和通道；在各入口原合同内初始化当前缓存后才发送任务动作。既有断电和本任务净空确认沿用，不重问；新执行范围的已授权时限从激活事务起算，不能把代码维护时间或重连当作暂停。增加任务次数或时限不改变单次位移、速度、反馈、故障及接触限制。

核验记录分别报告原失败、新预算授权、零 TX 管理激活、实际派发、物体任务、录像与停止状态。此入口没有检测实时物理状态，也没有力控或物理停止能力。真实插拔及完成后提交仍须实际图像与回执证明。

## 原预算内的图像超时接续

已授权本任务及修复阻碍、仍在原执行窗口内时，专用 `pair_continuation.prepare_continuation` / `activate_continuation` 支持一次同 run 的审计接续。它仅处理空载普通 RGB 关节段四帧均已返回、唯一失败原因为本段 RGB 到期、无未决发送或抓持的窄场景；其他故障不适用。旧宿主先正常关闭并退出，管理入口核对完整发送历史、关闭回执、故障后的双臂被动稳定采样及保存的新图空载语义。

新 scope 追加原合同到当前修复合同的记录，旧 scope、故障和失败事件保留；同 run 的已用次数、上限、起点和截止时间完全不变，不再索要同一剩余预算的授权。旧 owner 和旧 event 不能恢复发送，不把后来的静止观测改写为原事件成功。新宿主用新连接、新图和独立反馈按原入口建立当前缓存，不复制旧缓存或回放失败目标。管理激活仍是零 TX，不能声称物理已停止或任务已完成。

避免重复图像时效故障：先完成目标推理和必要准备，再取用于本段的新图；查看后紧接 `observe → submit`，不把解释、记账或其他准备插在图像与派发之间。RGB 初始化及 joint 分支在 claim 前预留至少原 3 秒基线和 3 秒稳定观察；余量不足返回 `refresh_required`，零事件、零步数、无新故障，此时只刷新当前图像后重新决定本步。普通/带载 joint 实际首帧前还保留至少 3 秒后验检查；若届时已经 claim 而拒绝发送，仍保留该事件及预算消耗，不悄悄回扣。最低余量不是完成保证，原 30 秒图像期限和所有运动约束不变。

## 原预算内的零发送新鲜度故障接续

已用过上述 RGB 到期接续后，`pair_continuation.prepare_zero_tx_continuation` / `activate_zero_tx_continuation` 另支持一次独立审计：当前 owner 只有完整限位查询、双臂初始化及最后一次空载普通 RGB 接近／对齐；最后事件的唯一设备错误必须为 `Joint feedback exceeded 50 ms including validation`，两臂发送尝试、已返回帧和阻挡帧均严格为零，且无原发送回执、未决、抓持或保持记录。逐项原始历史、关闭累计计数及查询／初始化／失败计划的连接身份必须相符；旧宿主关闭并退出后，绑定故障后的真实被动稳定记录、新图语义及当前已修复代码。归档证据不替代新宿主的当前反馈与图像。

该入口使用已有任务和修复授权，只追加独立的 `pair_predispatch_continuations` 范围；旧 RGB 接续表、全部故障、事件和合同不改，原开始时间、截止时间、已用次数及上限不变。全部历史 owner 均拒绝重新接管，旧失败 event 只返回原回执、不重发或退还次数；新宿主不继承缓存或限位来源。它不是通用清故障、任意零发送重试或新预算入口，也不声明物理停止或拔插成功。

## 干净结束后的显式新轮

当前有效范围已正常关闭、无 owner／活动 run／故障或未决事件，原窗口已到期，且历史属于 `pair_round` 支持的完整成功事件时，可在用户明确授权后追加新轮。原运行、历史故障、事件、已用次数及原期限不改；新轮另记父子关系和累计次数。不适用于活动宿主、部分发送、未解除抓持或保持事务，不能用新 ID 绕过这些条件。

现成管理 API 为 `robot_tools.pair_round.prepare_round(path, parent_run_id, *, close_log, new_run_id, started_at, max_steps=500, max_duration_s=3600, budget_start_policy="include_repair_time")`，以及 `activate_round(proposal, authorization, *, project_root)`。前者只读原账本和正常关闭证据并冻结当前代码及预算；后者在执行锁和事务中重新核对后追加记录。二者都不发送硬件帧，也不转移旧缓存或限位来源；新宿主按当前反馈建立本轮来源。

默认 `include_repair_time` 的 `started_at` 与新预算授权收到时间一致，离线修复也消耗该窗口。只有用户明确要求“修复后重新计时”时，选择 `after_repair_before_online_execution`：外层先完成修复与离线检验，再在首次在线执行前冻结 `started_at`；授权可以早于该起点，但必须来自原窗口到期后的真实用户消息。`authorization` 使用 `decision="authorize_explicit_new_round"`，绑定消息原话／引用／收到时间、proposal 哈希及准确 `new_budget`；修复后起算分支还须绑定同名 `budget_start_policy`。已有明确授权直接记录采用，不要求用户对同一预算重复回复。

截止时间固定为 `started_at + max_duration_s`，不是每次 activate、重连或修复时重新计算。起算后不暂停、不自动续时；需要另增预算仍须新的明确授权与适用入口。每轮上限为 500 次、3600 秒，不扩大任何单次动作守卫。当前新增能力先按离线验证报告，真实激活、派发及物体结果另据实际回执记录，不能把管理成功或正常 close 当作物理停止／拔插成功。
