# 已结束故障的审计接续

## 已完整开爪后原参考偏差的接续

支持式恢复开爪已经完整返回一帧、随后因原抓取本体参考偏差失败时，先保留失败并正常关闭宿主。用户已要求继续任务及修复、原预算仍有效时，使用 `supported_gripper_recovery.prepare_opening_continuation` / `activate_opening_continuation` 审计该特定状态；不重发旧开度，也不把后来的静止读数追认为旧动作成功。

先读真实账本状态；CLI 已返回失败不代表账本已保存回执。若原事件仍为 `pending`，由 `prepare_pending_opening_reconciliation` / `reconcile_pending_opening` 核对已关闭的原会话、完整帧返回及原故障，经过正常 `finish(success=False)` 补记遗漏的失败回执。保留原 pending 记录来源与实际故障时刻，记账完成时刻使用当前时间；不倒填、不清故障，也不给其它 pending 例外通行。无法核对原返回的事件仍不准接续。

入口核对原开爪帧、故障与关闭记录、故障后的三路新图及零 TX 本体稳定反馈。本体须回到原 candidate 锚点范围；最新爪宽只作为独立的残余开口参考，不替换本体锚点。被动记录只有最新夹爪值时，不声称它证明了整窗夹爪稳定；发送前由新宿主取得现有三秒完整基线。物体仍需可见的独立支撑，不能将分离不清楚写成空爪。

管理激活只追加一次原预算接续。新宿主先用 `robot_pair_recover_supported_gripper` 提出比旧请求和旧编码目标更大的新开度，仍受相对当前开口最多 5 mm 的限制；旧 owner、旧事件、故障和已用步数保留。需要进入普通空爪准备时，用动作后的新图调用 `robot_pair_confirm_recovery_release`，实际分离与新反馈成立才继续；分离不明确就保留未确认状态。用户改为要求在原支撑下重新试夹时，按下节另行审计该有限范围，不伪造分离。部分发送、其它故障或新开爪再次失败时停止新增动作，不循环接续或放宽关节边界。该流程不转移抓持、缓存或任务成功结论。

## 已成功开爪后的支持下重新试夹

用户已要求只用左臂试夹、右臂不动作，且最近支持式开爪完整成功、原宿主已经正常关闭时，可在原预算内追加 `reacquisition` 审计范围。核对原失败 probe、成功开爪事件及完整单帧回执、关闭记录、当前三路 RGB 与原独立支撑；保留旧故障、事件、已用步数及原截止时间。不要求物体已完全离开手指，不以 `object_clear_of_fingers` 或空爪声明代替当前接触事实。

管理层将原 candidate 本体参考与最近成功开爪的实际爪宽分别绑定到来源哈希。新宿主的首次物理操作通过 `reacquire_supported_gripper` 复用正常闭合 probe：发送前取得三秒完整本体及爪基线，两臂本体参考不替换，右臂零 TX，不继承或补建关节缓存。每次名义力 0.2、闭合不超过 5 mm；当前图像、反馈新鲜度、关节和漂移限制保持原值。

本范围最多三次闭合，每次经新 RGB、独立支撑描述和同一来源准入。仅前次完整成功为 `target_arrived` 且无候选时可再提出更窄的新目标；请求值和编码值均须小于前次目标，实际开口参考来自前次最终反馈。出现 `settled_contact_candidate` 后只允许新图加零 TX 保持核验；失败、部分或未知发送、支撑变化均停止新增动作。该范围不授予释放确认、空爪准备、右臂动作或单左臂拔出资格；调用字段与结果解释见[支持下重新试夹](../../piper-manipulation/references/bounded-contact.md#已开爪后在原支撑下重新试夹)。

## 支持下试夹零发送故障后的显式新轮

支持下重新试夹已经 claim、却在三秒基线期间因 RGB 过期失败，且所有单步与整宿主发送尝试、返回、阻挡计数均为零时，可经 `pair_round.prepare_round` / `activate_round` 的 `parent_kind="supported_contact_zero_tx_fault"` 接续。此入口核对完整原会话与 journal 前缀，确认没有发送意图、已发帧或接触 trace，原事件已完整记为失败，宿主正常关闭且不存在未决发送。一个 `prepare_probe` 形成的零版本 `empty` episode 仅作未形成候选的账本记录，不证明实物空爪。

旧窗口到期后，必须使用本次明确的新轮授权。沿用 `after_repair_before_online_execution`，修复和离线验证完成后、首次在线执行前冻结新起点；原起点、期限、已用步数（本次为 16 步）及故障不改。新 owner 和新事件另记，旧事件不重发，也不因零 TX 退还其局部尝试消耗。本阶段原三次尝试已消耗一次，新轮仅剩两次独立闭合；最近成功开爪的实际宽度及原本体参考保留，未发送的闭合目标不成为下一次必须更窄的依据。

新轮仍绑定原受限试夹范围：只允许同一左爪、同一物体在当前独立支撑下按新图闭合，最多 5 mm、原名义力，右臂及双臂本体不发送目标。候选形成后仅准零 TX 保持核验，不因 round ordinal 改变而放开普通动作、初始化或带载动作。新图与被动反馈须在正常关闭后取得，真正发送前仍用新连接完成三秒基线；此前不足三秒的失败采样不能补认为完整稳定窗口。

`close_log` 采用 `piper_contact_zero_tx_closure_v1` manifest，指向真实 session 日志及冻结 journal 前缀索引。索引覆盖整段 `session_started` 到 `session_ended`；排除的 `feedback` / `pair_fault_feedback` 仅为遥测，完整原始前缀、字节长度和哈希仍保留。部分或未知发送、其它故障、存在候选/持物记录或真实本体偏离时，不适用此入口。

## 试夹完整发送后重复身体参考误判的原预算接续

`supported_gripper_recovery.prepare_sent_contact_continuation` / `activate_sent_contact_continuation` 接续当前已授权轮内的一次完整左爪发送：原始错误来自新身体基线，而原 candidate 身体参考下的动作及故障后完整反馈均未越界。管理入口核对原单帧、正常资源关闭、空的记录状态及实际后续反馈，保留失败、故障和原预算。真实原参考超界、驱动异常、未知或部分发送不适用。

沿用本轮真实用户授权文件，不要求故障后重复授权，也不伪造新消息。最新实测爪宽单独放入 `completed_probe_continuation.residual_jaw_anchor`；原成功开爪来源和双臂身体参考不改。前面的零发送失败和本次已发送失败各占一次，原三次额度只剩一次；新的请求及编码目标都须比已发送目标更窄，并符合当前开口的 5 mm 单步上限。管理登记不发送命令，不转移抓持或缓存；后续仍读新 RGB 与新三秒反馈，由现有试夹入口派发一次。

## 已结束的初始化暂态故障接续

仅机械臂断电、电脑未重启时，电机启动使用[在线接续分流](online-readiness.md)中的 `robot_startup_after_arm_power_cycle`；其资格按本次机械臂断电事件与当前反馈判断，不按电脑启动时间判断。它不激活下文任何任务预算或清除原故障；任务恢复仍按适用合同另行核对。

历史任务审计现可识别随后追加的一次完整单臂断电启动记录：核对原 claim、请求、mode/enable 字节与返回计数、原始反馈、清理回执及启动前全部任务表哈希，只在内存中的旧父任务重建时排除此后发生的启动表。原数据库、启动记录、故障、预算和当前姿态准入均不变；未知新增表、历史被改动、未决或部分启动仍拒绝。该兼容处理不提供断电后新姿态任务接续，不取消旧目标邻近性或绝对关节范围要求，也不续期已到期的窗口。若只读审计通过，仍必须报告这些剩余条件，不能把表兼容修复写成可运动。

### 完整空载发送故障后，单臂断电后的新任务

用户明确要求修复后作为新任务重新开始，且失败臂已经完成另行记录的单臂断电启动时，可在 `pair_round.prepare_round(parent_kind="completed_unloaded_joint_fault", recovery_origin="arm_cycle_current_pose", budget_start_policy="after_repair_before_online_execution", task_file=...)` 中选择新姿态准备分支。原默认 `completed_target` 分支仍要求接近旧完整目标，不自动切换。

新分支仍核对原完整发送、空载故障、正常关闭、无未决发送/保持/抓持和原历史哈希；另要求同一电脑启动中的完整单臂启动 claim、真实两帧及反馈、失败臂身份一致、启动后新三秒静止反馈和三路 RGB。未断电的另一臂必须仍接近旧独立基线。重启臂新姿态须在固定官方 PiPER X 名义范围内，此项只允许建立准备会话，不替代当前控制器限位。原状态、故障、启动记录及累计次数全部保留，新预算由用户的新任务指令单独登记。

激活只能以 `connection_mode="prepare"` 打开；不继承旧目标、缓存、连接或限位，不重发旧动作。宿主必须重新采集控制器限位，现有首次目标及所有运动检查保持不变；若当前姿态与新回读限位冲突，停止在准备阶段并记录具体差异，不能以新任务或使能代替限位维护。离线验证与实机恢复结果分别记录。

这不是自动重试。原 `pair_scope`、故障、运行、回执及预算保留原值；新执行范围只有在用户明确同意故障后的新一轮有限预算后才创建。普通新 run-id、旧 owner、legacy 单步接口不能选用它；本次动作失败不改写为成功。

适用范围仅为：原运行已到期，只有完整厂家限位查询和最后一次 RGB 初始化；初始化四帧均有返回记录，唯一设备错误为 `joint_tracking_envelope`，无额外/未知帧、未决发送、保持或抓持历史；原宿主已有正常 close 回执，未遗留活动控制进程。close 只证明资源清理，不是机械停止。其他故障不得套用此入口。

`robot_tools.pair_restart.prepare_restart` 只读实际 SQLite 与原 close 日志，冻结全量历史摘要、原合同、当前修复源码、四帧及拟议预算，返回 proposal，不启动设备。默认新增执行窗口最多 900 秒；新步数与旧已用步数相加不得超出原步数上限。用户在故障后明确指定新的次数和时限时，使用 `budget_mode="explicit_user_budget_request"`，允许本次新窗口最多 1000 次、10800 秒；旧已用次数另行累计，原记录不清零。仅已激活且预算完全匹配的 execution epoch 可让新宿主采用该范围，普通新 run 不因此扩大。用户的旧 restart、未修改目标的自动续轮和沉默不作为这次新增预算授权。

外层操作者保存真实原话、消息引用及收到时间，才调用不对普通 robot tool 暴露的 `activate_restart`。针对既有 proposal 的确认使用 `authorize_audited_new_attempt`；故障后用户新的明确预算指令使用 `authorize_explicit_budget_request`，可先于随后生成的 proposal，但必须绑定准确新预算与 proposal 哈希。用户主动修订目标、明确给出本轮新预算也按后一分支记录，不因为消息载体是目标恢复而遗漏新增指令；不将没有新授权内容的自动续轮冒充用户确认。已有这种明确授权就直接接续，不再要求对同样预算二次回复。

该管理事务占用现有执行锁、重核当前历史与代码，追加一次新执行范围及父子审计记录；不清旧故障、不改原起点或期限、不复制缓存，不自动发任何硬件帧。授权重放、旧 owner 或任意新 ID 均不能创建第二份预算。准备 proposal 与离线测试不等于已经完成激活。

激活后的唯一新宿主仍用原固定工具：新反馈取得当前健康、静止及模式；新 RGB 取得双臂空载/无接触和通道；在各入口原合同内初始化当前缓存后才发送任务动作。既有断电和本任务净空确认沿用，不重问；新执行范围的已授权时限从激活事务起算，不能把代码维护时间或重连当作暂停。增加任务次数或时限不改变单次位移、速度、反馈、故障及接触限制。

核验记录分别报告原失败、新预算授权、零 TX 管理激活、实际派发、物体任务、录像与停止状态。此入口没有检测实时物理状态，也没有力控或物理停止能力。真实插拔及完成后提交仍须实际图像与回执证明。

## 原预算内的图像超时接续

已授权本任务及修复阻碍、仍在原执行窗口内时，专用 `pair_continuation.prepare_continuation` / `activate_continuation` 支持一次同 run 的审计接续。它仅处理空载普通 RGB 关节段四帧均已返回、唯一失败原因为本段 RGB 到期、无未决发送或抓持的窄场景；其他故障不适用。旧宿主先正常关闭并退出，管理入口核对完整发送历史、关闭回执、故障后的双臂被动稳定采样及保存的新图空载语义。

新 scope 追加原合同到当前修复合同的记录，旧 scope、故障和失败事件保留；同 run 的已用次数、上限、起点和截止时间完全不变，不再索要同一剩余预算的授权。旧 owner 和旧 event 不能恢复发送，不把后来的静止观测改写为原事件成功。新宿主用新连接、新图和独立反馈按原入口建立当前缓存，不复制旧缓存或回放失败目标。管理激活仍是零 TX，不能声称物理已停止或任务已完成。

避免重复图像时效故障：先完成目标推理、计划说明和必要准备，再取用于本段的新图；查看后紧接 `observe → submit`，不把解释、记账或其他准备插在图像与派发之间。RGB 初始化及 joint 分支在 claim 前要求大于 12 秒余量；普通/带载 joint 实际首帧前要求大于 9 秒。余量不足返回 `refresh_required` 时零事件、零步数、无新故障，只刷新图像后重新决定本步；若已经 claim 才拒绝发送，仍保留事件及预算消耗，不悄悄回扣。预留由 3 秒基线、6 秒运动/调度、3 秒稳定组成，是最低准入条件，不保证覆盖 20 秒最大观察等待；原 30 秒图像期限及反馈、运动约束不变。

## 原预算内的零发送新鲜度故障接续

已用过上述 RGB 到期接续后，`pair_continuation.prepare_zero_tx_continuation` / `activate_zero_tx_continuation` 另支持一次独立审计：当前 owner 只有完整限位查询、双臂初始化及最后一次空载普通 RGB 接近／对齐；最后事件的唯一设备错误必须为 `Joint feedback exceeded 50 ms including validation`，两臂发送尝试、已返回帧和阻挡帧均严格为零，且无原发送回执、未决、抓持或保持记录。逐项原始历史、关闭累计计数及查询／初始化／失败计划的连接身份必须相符；旧宿主关闭并退出后，绑定故障后的真实被动稳定记录、新图语义及当前已修复代码。归档证据不替代新宿主的当前反馈与图像。

该入口使用已有任务和修复授权，只追加独立的 `pair_predispatch_continuations` 范围；旧 RGB 接续表、全部故障、事件和合同不改，原开始时间、截止时间、已用次数及上限不变。全部历史 owner 均拒绝重新接管，旧失败 event 只返回原回执、不重发或退还次数；新宿主不继承缓存或限位来源。它不是通用清故障、任意零发送重试或新预算入口，也不声明物理停止或拔插成功。

## 干净结束后的显式新轮

当前有效范围已正常关闭、无 owner／活动 run／故障或未决事件，原窗口已到期，且历史属于 `pair_round` 支持的完整成功事件时，可在用户明确授权后追加新轮。原运行、历史故障、事件、已用次数及原期限不改；新轮另记父子关系和累计次数。不适用于活动宿主、部分发送、未解除抓持或保持事务，不能用新 ID 绕过这些条件。

现成管理 API 为 `robot_tools.pair_round.prepare_round(path, parent_run_id, *, close_log, new_run_id, started_at, max_steps=500, max_duration_s=3600, budget_start_policy="include_repair_time")`，以及 `activate_round(proposal, authorization, *, project_root)`。前者只读原账本和正常关闭证据并冻结当前代码及预算；后者在执行锁和事务中重新核对后追加记录。二者都不发送硬件帧，也不转移旧缓存或限位来源；新宿主按当前反馈建立本轮来源。

默认 `include_repair_time` 的 `started_at` 与新预算授权收到时间一致，离线修复也消耗该窗口。只有用户明确要求“修复后重新计时”时，选择 `after_repair_before_online_execution`：外层先完成修复与离线检验，再在首次在线执行前冻结 `started_at`；授权可以早于该起点，但必须来自原窗口到期后的真实用户消息。`authorization` 使用 `decision="authorize_explicit_new_round"`，绑定消息原话／引用／收到时间、proposal 哈希及准确 `new_budget`；修复后起算分支还须绑定同名 `budget_start_policy`。已有明确授权直接记录采用，不要求用户对同一预算重复回复。

截止时间固定为 `started_at + max_duration_s`，不是每次 activate、重连或修复时重新计算。起算后不暂停、不自动续时；需要另增预算仍须新的明确授权与适用入口。每轮上限为 1000 次、10800 秒，不扩大任何单次动作守卫。当前新增能力先按离线验证报告，真实激活、派发及物体结果另据实际回执记录，不能把管理成功或正常 close 当作物理停止／拔插成功。

用户指定三小时、1000 次时显式传入 `max_steps=1000, max_duration_s=10800`；函数保留原保守默认值，新最大值不修改旧账本的预算、期限或历史累计。

## 完整发送后图像到期的显式新轮

旧轮已到期且用户明确要求修复后重新开始时，同一 `pair_round` 管理 API 的 `parent_kind="postsend_rgb_expiry_fault"` 支持这个特定退出状态：此前限位查询、初始化和空载 RGB 接近/对齐全部完整成功，末动作四帧均已返回，唯一设备错误为原始 `visual_rgb_expired`。宿主须已正常关闭、无持物/接触/保持或未决发送；管理入口核对原始事件、计划和 RGB 摘要、绑定、累计帧数、故障与关闭记录，要求当前宿主及适配器已修复。未知或部分发送、其他错误不能套用。

`recovery_evidence` 绑定故障后的双臂零 TX 三秒以上被动记录、保存的三路 RGB 及实际空爪/无接触语义。这条新分支使用已有四元数两两姿态距离测量整段 SO(3) 旋转直径，同时保留欧拉角跨度和计算方法供审计；整体旋转仍最多 0.003 rad，逐关节、逐欧拉轴、平移、健康和时间限制不变。旧接续默认的欧拉跨度上界合同不改。归档恢复证据不替代新宿主的当前图像及反馈。

新轮仍需绑定真实的新预算授权，采用 `after_repair_before_online_execution`，修复和离线检验完成后再冻结起点。激活只追加审计范围，保留原失败、故障、旧 owner、累计次数和原期限；不清故障、不转移缓存、不重放末目标。自动续轮、重复同一未修改目标或代码升级本身不授予新预算。

历史中至多一次成功的空爪位置模式开爪 `gripper/approach` 可由同一分支单独审计：原请求、发送前和发送后的开口须证明实际张开，原回执须满足既有到位、稳定窗口与新鲜反馈要求，完整单帧发送计数及另一臂零发送须一致。开爪前后相邻的同臂成功 RGB 关节动作必须保留空载语义及原图哈希，且全历史没有抓持 episode。试夹、闭爪、释放、未知发送或缺失证据仍拒绝。该扩展只读取旧证据，不让重启后的 P 模式、未使能夹爪或不稳定反馈自动获得接续资格。

## 主机重启后的新现场监督任务准备准入

`robot_tools.pair_task_enrollment.prepare_task` / `activate_task` 是独立的窄范围管理入口，不改变上述旧接续合同。仅覆盖已审计的空载完整发送 RGB 到期历史、原宿主正常关闭，以及当前 Linux boot 中双臂各一次 mode/enable 的已知四帧启动。该启动原结果必须仍为特定右关节漂移失败；管理入口核对两条失败 claim、原 request/result、四次 intent/return 的字节、侧、时间和累计计数，以及完整原始反馈与漂移，不能将失败改写为成功或重试启动。旧运行、故障、owner、启动失败和预算全部保留；未决、未知/部分发送、抓持、保持、其他错误或当前控制宿主均拒绝。

新任务文件是 `schema="piper_supervised_plug_task_v1"` 的 envelope：`task` 必须精确匹配现成 `robot_pair_open` 构造的 `task_id="plug_transfer_left"`、双侧 `roles="task"` 和 `site_context.workspace_clearance`；另以 `recipe_path`、`recipe_sha256` 绑定当前 canonical recipe，以 `on_site_supervision={"source":"user","statement":实际原话}` 记录现场监督。电源、物体身份等实际证据可留在 envelope 中，不增加工具参数或伪造任务合同字段。完整文件与图片字节摘要绑定提案；语义描述须保留实际所见，不能将未知轻触写成已证明无接触。

`prepare_task(path, parent_run_id, *, close_log, task_file, new_run_id, started_at, passive_paths, rgb_observation, visual_observation, max_steps=1000, max_duration_s=10800)` 只读审计。被动反馈和三路 RGB 必须在该启动完成后采集，并在审计时不超过原 30 秒图像窗口。归档准入接受健康 CAN 控制、P/J/L、六关节已使能及已知布尔夹爪使能标志；当前代码仍需完整三秒递增原始 trace、逐关节 0.003 rad、位置范数 0.0005 m、真正 SO(3) 旋转直径 0.003 rad。欧拉分量跨度保留作诊断，不用 wrap/gimbal 坐标放大替代实际旋转。已观察到的本地/控制命令流拒绝；未观察到外部命令不能证明总线独占。

2026-10-08 用户随后明确允许已观察的右 J4 小幅波动，并要求固化以避免再次卡住。原文“当前右 J4 不因可能是误差而忽略”不再作为否定这次授权的规则。后续代码已提供当前插头任务专用的 `right_j4_bounded_v1`（0.5°），新任务准入与打开宿主携带相同授权字段，按[反馈波动处理](feedback-tolerance.md)接续；不重复索取同一许可或反复采样证明同一超差。旧失败照实保留，文档许可不直接改变宿主数值检查或产生发送资格。

`activate_task(proposal, authorization, project_root=...)` 仅在真实新任务授权与全部证据匹配时，在共享执行锁和事务内追加 `pair_runs`/`pair_rounds`。授权字段为 `source="user_message"`、真实 `message_id/statement/received_at`、`decision="authorize_explicit_new_round"`、准确 `proposal_sha256/new_budget` 和 `budget_start_policy="after_repair_before_online_execution"`。先完成离线修复与测试，再冻结新任务开始时刻；已有明确新任务预算偏好沿用，不能利用重连移动截止时间。激活重新核对 boot、历史、源码、当前证据及其时效；准备失败不写账本或分配新范围。
